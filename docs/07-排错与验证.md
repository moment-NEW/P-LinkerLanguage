# 排错与验证

链接布局问题有三个层次：生成器是否理解布局、链接器是否按预期放置 section、目标板启动代码是否完成了运行时复制。必须逐层验证，不要只看“编译通过”。

## 1. 生成器阶段

先单独运行生成命令：

```powershell
python tools/generate_linker.py example/layout.pl.c --toolchain gnu --linker-out build/pl_sections.ld --header-out build/generated/pl_linker_symbols.h
```

### 常见错误

| 报错或现象 | 原因 | 处理方式 |
| --- | --- | --- |
| `memory regions overlap` | 两个 `pl_memory_t` 的地址范围重叠。 | 核对芯片手册、Flash/RAM bank 起点与容量。 |
| `references undefined memory` | `PL_REF(name)` 的名字不存在或拼写不一致。 | 对照 `pl_memories[]` 中的 `.name`。 |
| `alignment must be a non-zero power of two` | 对齐不是 1、2、4、8 等。 | 使用 2 的幂。 |
| `reserved region ... requires fixed size` | 保留区域用了 `PL_LINKER_SIZE`。 | 改为固定 `PL_KIB()` 或数值大小。 |
| `RAM code region ... requires load memory` | RAM 执行代码没有定义加载位置。 | 设置 `.load_memory = PL_REF(FLASH)`。 |
| `unsupported #if condition` | 使用了当前条件筛选器不支持的预处理表达式。 | 简化为 `defined()`、`#ifdef` 等，或升级为真实编译器预处理。 |
| `unsupported character` | 布局数组或其附近出现解析器不识别的 C 语法。 | 保持布局文件为受控 C 子集；参见 [06-生成器原理](06-生成器原理.md)。 |

## 2. 编译阶段

### 找不到生成头文件

报错：

```text
pl_linker_symbols.h: No such file or directory
```

原因是生成器没有在编译前运行，或编译器 include 路径不包含生成目录。

GNU Arm 示例：

```text
-Iinc -Ibuild/generated
```

ARMClang 示例：

```text
-Iinc -Ibuild/armclang_generated
```

不要把两种后端生成的符号头混用。ARMClang 头含有 `__asm("Image$$...")` 绑定，GNU 编译器不应使用它。

### `PL_INIT` 或 `PL_RAMFUNC` 没有生效

检查：

1. 源文件是否包含 `pl_linker.h`。
2. `group` 是否精确匹配布局区域的 `.name`。
3. 宏是否在函数定义之外使用。
4. 目标文件中是否确实存在期望输入 section。

GNU 工具链可检查：

```powershell
arm-none-eabi-objdump -h build/main_arm.o
```

应找到类似：

```text
.pl.init.app_init.010
.pl.ram_code.fast_code
```

## 3. 链接阶段

### `undefined reference to pl_*_start`

常见原因：

- 链接命令没有使用生成的 `.ld` 或 `.sct`。
- 生成了一个布局区域，但实际链接脚本未包含该区域。
- C 编译时使用了旧的生成头文件。

处理：先删除或覆盖旧 `build` 产物，重新生成，然后检查链接选项。

### 初始化函数被裁剪

GNU 后端对 `PL_LINK_INIT` 使用：

```ld
KEEP(*(SORT_BY_NAME(.pl.init.app_init.*)))
```

若最终表为空，确认：

- `PL_INIT` 的 group 与区域名一致。
- 链接器用的是新生成的脚本。
- 没有其他脚本规则在此规则之前吞掉了相同输入 section。

### RAM 函数仍在 Flash

检查 ELF：

```powershell
arm-none-eabi-nm -n build/demo.elf
```

预期：

```text
08000008 A pl_fast_code_load_start
20000000 T pl_fast_code_start
2000000c T pl_fast_code_end
```

运行地址应落在 RAM 地址范围，加载地址应落在 Flash 范围。若 `motor_control_step` 不在 RAM 区间，常见原因是 `PL_RAMFUNC(fast_code)` 与布局名不匹配，或输入 section 模式被其他规则先收集。

### 固定保留区冲突

`PL_LINK_RESERVED` 在生成器内部只检查当前布局对象，不知道原始启动脚本、heap、stack 的具体位置。即使链接成功，也应检查：

```text
共享区范围、.data、.bss、heap、stack、DMA buffer、bootloader 合同区
```

任何两个范围发生重叠都会造成运行时内存破坏。

## 4. 目标板运行阶段

### RAM 函数第一次调用就 HardFault

可能原因：

- 没有调用 `copy_fast_code()`。
- 复制长度错误。
- RAM 没有被配置为可执行，或存在 MPU/TrustZone 限制。
- RAM 函数间接调用了仍在 Flash 的代码。
- 中断在复制完成前进入 RAM 函数。

建议顺序：

```text
复位
  -> 初始化堆栈
  -> 复制标准 .data
  -> 清零 .bss
  -> 复制所有 PL_LINK_RAM_CODE 区域
  -> 配置必要的 MPU/cache
  -> 执行自动初始化
  -> 进入 main
```

### 初始化顺序不符合预期

GNU 后端按 section 名排序。优先级应固定宽度：

```c
PL_INIT(app_init, 005, early_init);
PL_INIT(app_init, 010, clock_init);
PL_INIT(app_init, 100, application_init);
```

不要混用 `1`、`10`、`100`，因为字符串排序会得到 `1`、`10`、`100`，而不是你可能期望的数值序列。ARMClang 后端的 section 排序策略应以 map 文件实际结果为准；对必须严格排序的生产需求，应在后端增加明确的排序/区域拆分策略并做自动测试。

## 5. 发布前检查清单

- [ ] 内存区地址和容量与芯片手册一致。
- [ ] 生成命令进入构建依赖图，而不是依赖人工执行。
- [ ] 所有 `PL_INIT` / `PL_RAMFUNC` group 都有对应区域。
- [ ] RAM 代码都有加载内存和启动复制逻辑。
- [ ] map / ELF / AXF 中的运行地址、加载地址与预期一致。
- [ ] 固定保留区不与 `.data`、`.bss`、heap、stack、bootloader 区重叠。
- [ ] 在目标板上验证初始化顺序和 RAM 函数首次调用。
- [ ] 在开启优化、LTO、链接垃圾回收的正式构建配置下再次验证。
