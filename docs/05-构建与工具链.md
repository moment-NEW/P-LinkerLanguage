# 构建与工具链

生成器必须在依赖 `pl_linker_symbols.h` 的 C 文件编译前运行。完整构建顺序如下：

```text
1. 生成 .ld / .sct 和 pl_linker_symbols.h
2. 编译业务 C 文件
3. 链接目标文件
4. 检查 map 或 ELF/AXF 中的区域地址
5. 烧录并在目标板验证启动复制和初始化顺序
```

## GNU Arm Embedded Toolchain

### 生成

```powershell
python tools/generate_linker.py example/layout.pl.c --toolchain gnu --linker-out build/pl_sections.ld --header-out build/generated/pl_linker_symbols.h
```

### 编译

需要包含公共头和生成头：

```powershell
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -ffreestanding -Iinc -Ibuild/generated -c example/main.c -o build/main_arm.o
```

如果你也把 `layout.pl.c` 当普通 C 文件编译，需定义对应分支：

```powershell
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -DPL_TOOLCHAIN_GNU -Iinc -c example/layout.pl.c -o build/layout_gnu.o
```

注意：布局数组是生成器的输入，当前 demo 不要求将 `layout_gnu.o` 链接进最终镜像。

### 链接

最小演示：

```powershell
arm-none-eabi-ld -T build/pl_sections.ld build/main_arm.o -o build/demo.elf
```

真实工程不能直接把 demo 的完整 `MEMORY` / `SECTIONS` 文件叠加到已有 `.ld` 而不检查冲突。原因是大多数芯片模板已经定义了：

- `MEMORY` 区域。
- 中断向量表。
- `.text`、`.rodata`。
- `.data` 的 Flash 加载地址与 RAM 运行地址。
- `.bss`、heap、stack。

有两种接入策略：

1. **布局文件成为唯一来源**：由生成器逐步扩展，最终生成完整芯片脚本。这适合新项目。
2. **扩展已有脚本**：将生成器输出改造成仅含自定义 section 的 fragment，再由原脚本 `INCLUDE`。这更适合已有 BSP。

当前 demo 验证前者的链接语义，还未实现无 `MEMORY` 的 fragment 输出模式。迁移旧工程前需要先实现该模式，或人工合并生成 section。

### 检查符号

```powershell
arm-none-eabi-nm -n build/demo.elf
```

预期能看到类似：

```text
08000000 R pl_app_init_start
08000008 R pl_app_init_end
08000008 A pl_fast_code_load_start
20000000 T pl_fast_code_start
2000000c T pl_fast_code_end
```

这说明初始化表在 Flash，RAM 函数的镜像在 Flash 而执行地址在 RAM。

## Arm Compiler 6 / ARMClang

### 生成

```powershell
python tools/generate_linker.py example/layout.pl.c --toolchain armclang --linker-out build/pl_sections.sct --header-out build/armclang_generated/pl_linker_symbols.h
```

### 编译

```powershell
armclang --target=arm-arm-none-eabi -mcpu=cortex-m4 -ffreestanding -Iinc -Ibuild/armclang_generated -c example/main.c -o build/main_armclang.o
```

若编译布局源本身：

```powershell
armclang --target=arm-arm-none-eabi -mcpu=cortex-m4 -DPL_TOOLCHAIN_ARMCLANG -Iinc -c example/layout.pl.c -o build/layout_armclang.o
```

### 链接

```powershell
armlink --scatter=build/pl_sections.sct --entry=your_reset_handler build/main_armclang.o -o build/firmware.axf
```

真实固件必须把 `--entry` 指向有效的 reset handler 或由启动文件提供入口。demo 使用普通函数仅为了验证布局，不代表板级启动方案。

生成 scatter 文件目前会加入一个 `ER_DEFAULT_RO` 的 `.ANY (+RO)` 兜底区，以便把不属于本库专用 section 的只读代码放入 Flash。生产工程仍需自行规划：

- 向量表位置。
- RW/ZI 数据区。
- stack / heap。
- 多个 load region。
- 特定芯片的安全区、外部存储器、ITCM/DTCM。

### 检查 AXF

```powershell
fromelf --text -s build/firmware.axf
```

可检查：

```text
Image$$ER_APP_INIT$$Base
Image$$ER_APP_INIT$$Limit
Load$$ER_FAST_CODE$$Base
Image$$ER_FAST_CODE$$Base
Image$$ER_FAST_CODE$$Limit
```

虽然 ARMClang 真实符号名不同，生成的 `pl_linker_symbols.h` 已将 C 中的 `pl_fast_code_start` 等名称映射到它们。

## CMake / Make 的依赖关系

无论使用何种构建系统，核心是声明生成文件是 `main.c` 的编译前置依赖：

```text
layout.pl.c + generate_linker.py + pl_linker_layout.h
    -> generated/pl_linker_symbols.h + pl_sections.ld
    -> main.c compilation and final link
```

不要只把生成器写成手工前置步骤，否则修改布局后很容易忘记重新生成。

## 编辑器诊断

若 VS Code 报 `pl_linker.h file not found` 或在 `layout.pl.c` 报未定义宏，通常是 IntelliSense 缺少：

- include 路径：`inc` 与当前后端生成头目录。
- 宏定义：GNU 使用 `PL_TOOLCHAIN_GNU`，ARMClang 使用 `PL_TOOLCHAIN_ARMCLANG`。

这属于编辑器编译配置问题，不等于实际构建失败。仍应以目标工具链的编译和链接结果为准。
