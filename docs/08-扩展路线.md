# 扩展路线

当前 demo 已经有适合扩展的基础：布局 C 结构体、解析后的 `Memory` / `Region` 中间表示、语义验证、GNU 与 ARMClang 两个渲染器。扩展应优先修改中间表示和验证规则，再为每个后端添加渲染，而不是把某个链接器的特殊语法塞进 `layout.pl.c`。

## 1. 扩展原则

### 布局 C 文件保持抽象

应继续描述：

```text
区域类型、运行内存、加载内存、地址、大小、对齐、边界符号、输入策略
```

不应出现：

```text
GNU ld 的 KEEP / LOADADDR / AT >
scatter 的 LR_ / ER_ / Image$$
```

这些都是后端职责。工具链差异首先由生成器的 `--toolchain` 和条件筛选处理。

### 每种区域类型必须完整定义语义

增加枚举值前，先写清楚：

1. 它收集哪些输入 section。
2. 是否需要运行内存和加载内存。
3. 它的大小是固定还是由链接器决定。
4. 是否需要起止符号和加载符号。
5. GNU 与 ARMClang 后端分别如何表示。
6. 如何在 ELF/AXF 中验证。

仅增加一个 enum 值但没有后端规则，会产生“布局文件可写但链接无意义”的接口。

## 2. 推荐的下一步功能

### A. GNU fragment 模式

这是最优先的工程化能力。

当前 GNU 输出含有：

```ld
MEMORY { ... }
SECTIONS { ... }
```

它适合 demo，但旧 BSP 通常已经定义 `MEMORY`。建议增加：

```text
--gnu-mode full
--gnu-mode fragment
```

`fragment` 只生成用户区域，并让项目原始脚本在适当位置 `INCLUDE`。这需要明确：自定义 section 应插入 `.text`、`.data`、`.bss` 的前后哪个位置，以及是否允许原脚本使用已有 `FLASH` / `RAM` 名称。

### B. 自动复制表

现在每个 RAM 区域都需要手写复制函数。可新增：

```c
PL_LINK_COPY_TABLE
```

或在 `pl_link_region_t` 增加 copy 策略，由生成器创建统一条目：

```c
typedef struct {
    const uint8_t *source;
    uint8_t *destination;
    size_t size;
} pl_copy_entry_t;
```

启动代码就能遍历所有 RAM 区域。实现时需要保证该表本身位于启动时已可访问的 Flash 中，并为 GNU/ARMClang 生成一致的符号适配。

### C. 零初始化表

可以增加需要在复位时清零的区域类型，例如 DMA buffer 区或自定义 BSS 区。其行为为：

```text
运行地址在 RAM
没有 Flash 加载映像
启动时 [start, end) 填零
```

它与 `RESERVED` 不同：`RESERVED` 是地址规划，不承诺初始化；zero-init 区域承诺复位后为 0。

### D. 通用输入规则

当前区域类型把输入模式固定在：

```text
.pl.init.<name>.*
.pl.ram_code.<name>
```

后续可增加 `pl_link_input_t`：

```c
typedef struct {
    const char *pattern;
    uint32_t flags;
} pl_link_input_t;
```

其中 flags 可表达 keep、排序、只读/读写分类。先在 IR 表达这些抽象操作，再映射为 GNU 的 `KEEP` / `SORT_BY_NAME` 和 ARMClang 可实现的等价策略。

### E. 多个 RAM bank

实际芯片常有 ITCM、DTCM、SRAM1、SRAM2、AXI SRAM、外部 SDRAM。当前 `pl_memory_t` 已能描述多个 bank。下一步是加强验证：

- 固定地址必须落在所属 memory 内。
- 固定范围不能超出 memory 终点。
- 显式地址的区域不能相互重叠。
- 在 map/ELF 后处理阶段检查实际自动区域是否越界。

### F. 链接后验证

这是从 demo 到可靠工具最关键的一步。链接前无法获知 `PL_LINKER_SIZE` 的最终大小，因此需要解析：

```text
GNU: ELF section table、map 文件、nm 输出
ARMClang: AXF、fromelf 输出、map 文件
```

验证每个区域：

```text
start <= end
start/end 位于预期运行内存
load symbol 位于预期加载内存
固定区域没有被覆盖
区域实际大小不超出所属 memory
```

失败时应报告区域名、预期范围、实际范围和来源 map/ELF 文件。

## 3. 测试策略

建议为生成器添加 Python 单元测试，至少包含：

- token 识别注释、字符串、嵌套初始化器。
- `#if/#elif/#else` 分支选择。
- 所有受支持数值表达式。
- 非法 memory、对齐、重复 name、重叠范围。
- 每个区域类型的 GNU 输出快照。
- 每个区域类型的 scatter 输出快照。
- 用本机真实 GNU Arm 和 ARMClang 进行集成链接测试。

对后端输出，不应只比较文本。还应链接一个最小目标文件并检查最终符号地址。

## 4. 不建议的扩展方向

- 不要用一个巨大正则直接匹配完整 C 结构体和嵌套括号。
- 不要让 Python 猜测任意用户结构体的字段语义。
- 不要在业务代码中散布 GNU / ARMClang 的 `#if`。
- 不要在未解析原始 BSP 脚本的情况下宣称固定区域绝不会和 stack/heap 冲突。
- 不要把未验证的编译器专有语法写入通用布局模型。

## 5. 建议的实施顺序

1. 为当前生成器补充单元测试和链接后验证。
2. 实现 GNU fragment 模式，先安全接入已有 BSP。
3. 自动生成 copy / zero 表，减少启动代码重复。
4. 增加通用输入规则和新的区域类型。
5. 再处理多 bank 分配、overlay、堆栈规划和复杂表达式。

这个顺序先解决“现有项目能安全使用”，再增加语言表现力。
