# 生成器原理

`tools/generate_linker.py` 的目标不是解析完整 C。它把布局文件限制为一个可验证的 C 子集：指定类型的全局数组和指定初始化器。这样可以享受 C 结构体的可读性，又不会在 Python 中重写一个 C 编译器。

## 整体流程

```text
layout.pl.c
    -> 条件编译筛选
    -> 正则词法分析
    -> 受控初始化器解析
    -> Memory / Region 中间表示
    -> 语义验证
    -> GNU ld 或 ARMClang scatter 渲染
    -> C 符号头文件渲染
```

## 1. 条件编译筛选

命令中的：

```text
--toolchain gnu
```

定义逻辑宏 `PL_TOOLCHAIN_GNU`；`--toolchain armclang` 定义 `PL_TOOLCHAIN_ARMCLANG`。

在词法前，`filter_conditionals()` 只保留选中的代码分支。支持：

```c
#if defined(PL_TOOLCHAIN_GNU)
#ifdef PL_TOOLCHAIN_ARMCLANG
#ifndef SOME_FLAG
#elif defined(...)
#else
#endif
```

也支持 `#if 0` 与 `#if 1`。不支持任意复杂的预处理表达式或宏展开。

设计意图是把工具链区分集中在 Python 输入阶段；布局结构本身不出现 GNU ld 或 scatter 专有字段。

## 2. 正则词法分析

`TOKEN_PATTERN` 使用正则识别：

- 空白与 C 注释。
- 字符串字面量。
- 十进制与十六进制整数。
- C 标识符。
- 布局子集需要的标点和运算符。

每个 token 都携带行和列，因此语法错误可报告为：

```text
line 42, column 17: expected '}', found ';'
```

正则只负责把字符流变为 token 流。花括号嵌套、数组、函数式宏和字段初始化由后续 parser 处理，不能用单个正则安全完成。

## 3. 解析的 C 子集

解析器只搜寻：

```c
const pl_memory_t something[] = { ... };
const pl_link_region_t something[] = { ... };
```

它支持：

- 指定初始化器：`.field = value`。
- 嵌套 `{ ... }` 数组初始化。
- 字符串与整数。
- `|`、`+`、`-`、`<<`、`>>`。
- `PL_KIB()`、`PL_MIB()`、`PL_REF()`、`PL_SYMBOL()`。

它会跳过其他普通 C 声明，例如工具链标记字符串或函数声明。

当前不支持：

- 完整宏展开。
- `sizeof`、三元表达式、逻辑表达式、函数调用求值。
- 复杂 C 声明符、结构体定义推导、跨文件符号解析。
- 根据 `typedef` 重命名识别布局类型。

布局描述必须直接使用这两个类型名，且不要在 `PL_REF`、`PL_SYMBOL`、`PL_KIB` 外再套自定义宏。

## 4. 中间表示与验证

解析后转换为 Python dataclass：

```text
Memory(name, origin, size, attributes)
Region(name, kind, memory, load_memory, address, size, alignment, ...)
```

生成前检查：

- 至少一个 memory 和一个 region。
- 内存区与区域名称唯一且符合标识符格式。
- 内存区地址范围不重叠。
- 区域引用的 memory 存在。
- 对齐为非零 2 的幂。
- `PL_LINK_RESERVED` 必须提供固定大小。
- `PL_LINK_RAM_CODE` 必须提供加载内存。

当前不会在 Python 中预先计算 `PL_LINKER_SIZE` 区域后的准确自动地址，因为这些大小只有链接器收集真实输入 section 后才知道。顺序与实际地址最终由链接器解决。

## 5. GNU 后端

GNU 后端生成：

```ld
MEMORY { ... }
SECTIONS { ... }
```

区域类型与输出规则：

| 类型 | 输入选择器 | 特殊行为 |
| --- | --- | --- |
| `PL_LINK_INIT` | `.pl.init.<name>.*` | `KEEP`，并按名称排序。 |
| `PL_LINK_RAM_CODE` | `.pl.ram_code.<name>` | 可生成 `> RAM AT > FLASH` 与 `LOADADDR`。 |
| `PL_LINK_RESERVED` | 无 | `NOLOAD` 并推进位置计数器。 |

## 6. ARMClang 后端

ARMClang 后端生成 scatter 的 Load Region / Execution Region：

```text
LR_FLASH ...
{
  ER_APP_INIT ...
  {
    *(.pl.init.app_init.*)
  }
}
```

`PL_LINK_RESERVED` 生成 `EMPTY` execution region。对于用户请求的边界符号，头文件映射到 `armlink` 的 `Image$$ER_name$$Base/Limit`，RAM 代码加载地址映射到 `Load$$ER_name$$Base`。

## 7. 为什么不是直接调用 C 预处理器

真实项目后续可以升级为调用 `arm-none-eabi-gcc -E` 或 `armclang -E`，使芯片定义和项目宏得到完整展开。当前 demo 自己处理有限的 `#if` 是为了演示“工具链判断发生在 Python 前端”这一原则。

接入实际复杂工程时，推荐把预处理作为单独阶段：

```text
layout.pl.c --(目标编译器 -E)--> 预处理 C --(本解析器)--> IR
```

但要保证关键 DSL 宏保留为解析器可识别的形式，或定义专用 `PL_LINKER_EXTRACT` 宏模式。
