# 业务代码接口

业务模块不直接写 GNU ld 或 scatter 文件。它们只包含：

```c
#include "pl_linker.h"
#include "pl_linker_symbols.h"
```

`pl_linker.h` 是手写公共头文件；`pl_linker_symbols.h` 是生成文件，必须先运行生成器。

## `PL_INIT(group, priority, function)`

原型：

```c
PL_INIT(group, priority, function)
```

例如：

```c
static void board_clock_init(void)
{
}

PL_INIT(app_init, 010, board_clock_init);
```

宏会生成一个静态 `pl_init_entry_t` 对象：

```c
typedef struct {
    pl_init_fn_t function;
} pl_init_entry_t;
```

并放入输入 section：

```text
.pl.init.app_init.010
```

### 参数约束

| 参数 | 约束 |
| --- | --- |
| `group` | 必须与 `PL_LINK_INIT` 区域的 `.name` 完全一致。 |
| `priority` | 建议使用固定宽度十进制 token，例如 `010`、`020`、`100`。 |
| `function` | 无参数、返回 `void` 的函数。 |

`PL_INIT` 的实现使用 `used` 属性，避免未被普通 C 调用的注册条目在编译阶段被删除。GNU 后端的 `KEEP` 进一步避免链接垃圾回收删除它。

### 执行初始化表

```c
void run_app_init(void)
{
    const pl_init_entry_t *entry;

    for (entry = pl_app_init_start; entry < pl_app_init_end; ++entry) {
        entry->function();
    }
}
```

调用时机由项目决定。通常在时钟、C 运行时 `.data` 复制和 `.bss` 清零完成后，在 `main()` 之前或 `main()` 开头调用。

初始化函数不应假定其他同优先级模块的执行顺序。若有依赖关系，应分配不同优先级，例如：

```c
PL_INIT(app_init, 010, board_clock_init);
PL_INIT(app_init, 020, uart_driver_init);
PL_INIT(app_init, 030, application_init);
```

## `PL_RAMFUNC(group)`

原型：

```c
PL_RAMFUNC(group)
return_type function(arguments)
{
}
```

例如：

```c
PL_RAMFUNC(fast_code)
void flash_safe_interrupt_handler(void)
{
}
```

该函数的输入 section 为：

```text
.pl.ram_code.fast_code
```

`fast_code` 必须对应一个 `.type = PL_LINK_RAM_CODE` 的布局区域。

### 必要的复制步骤

链接器只定义“函数的运行地址在 RAM、初始映像在 Flash”；它不会自动在复位时复制。启动代码必须显式复制：

```c
void copy_fast_code(void)
{
    uint8_t *destination = pl_fast_code_start;
    const uint8_t *source = pl_fast_code_load_start;

    while (destination < pl_fast_code_end) {
        *destination++ = *source++;
    }
}
```

复制长度是：

$$
size = pl\_fast\_code\_end - pl\_fast\_code\_start
$$

必须在第一次调用对应 RAM 函数之前完成复制。对需要在 Flash 擦除、编程期间执行的函数，这通常是启动序列的强制步骤。

### RAM 函数的实际限制

给函数加 `PL_RAMFUNC` 不意味着它的所有依赖都会自动转入 RAM。若 `flash_safe_interrupt_handler()` 调用另一个仍在 Flash 的函数，Flash 忙时仍可能出错。需要检查：

- 被调用函数是否也要放入同一 RAM 区域。
- 只读常量和跳转表是否会被访问。
- 中断向量表、Flash 驱动和缓存控制是否满足芯片要求。
- 编译器是否生成跨 section 的 veneer 或库函数调用。

最终应通过 map/ELF 检查调用图和 section 归属。

## 边界符号 API

生成器以布局中指定的名字生成头文件。例如：

```c
.start_symbol = PL_SYMBOL(pl_shared_buffer_start),
.end_symbol = PL_SYMBOL(pl_shared_buffer_end),
```

在 C 中：

```c
extern uint8_t pl_shared_buffer_start[];
extern uint8_t pl_shared_buffer_end[];
```

使用方式：

```c
uint8_t *buffer = pl_shared_buffer_start;
size_t length = (size_t)(pl_shared_buffer_end - pl_shared_buffer_start);
```

对于 `PL_LINK_INIT`，开始和结束符号的元素类型是 `pl_init_entry_t[]`，因此可以直接用指针遍历。对其余区域，元素类型是 `uint8_t[]`。

## 跨工具链符号一致性

GNU ld 直接生成用户请求的 `pl_*` 符号。ARMClang 中，`armlink` 自动生成以下符号：

```text
Image$$ER_FAST_CODE$$Base
Image$$ER_FAST_CODE$$Limit
Load$$ER_FAST_CODE$$Base
```

ARMClang 版本的生成头文件使用 `__asm("...")` 把用户可见的符号绑定到这些自动符号：

```c
extern uint8_t pl_fast_code_start[] __asm("Image$$ER_FAST_CODE$$Base");
```

因此业务代码不需要写 `#if defined(__ARMCC_VERSION)` 来区分链接器。
